# 代码规范

命名与类型表达「是什么」；注释表达「为什么 / 约束」；结构选择跟语义走；契约变更默认一次切齐。

## 使用说明

**强度**（依条款措辞判定）：

- **必须 / 禁止** — 不通过 review；可 lint 化的优先做成 lint。
- **应当 / 避免** — 默认遵守，违反须在代码注释或 PR 描述中说明。
- **建议 / 启发** — 经验性指引，按场景判断。

## 1. 注释：补命名与类型给不了的信息

命名表达局部「是什么」，类型表达形状与通道；注释表达**为什么、分几步、顺序约束、副作用、跨行不变量、与邻模块边界**。

命名 / 类型已表达的不写。有意图、顺序约束、副作用、跨模块契约时必须写——不得以「名称自解释」省略这类信息。

自检：遮住代码只读注释，能否得到代码给不了的信息（意图 / 顺序 / 约束 / 边界）？不能 → 删；该有却没有 → 补。

注释默认使用中文。

### 1.1 文件头

`src/**` 与测试文件均须以 JSDoc 文件头开头（置于 import 之前）：

```typescript
/**
 * @file 一句话：这个文件是什么 / 管什么
 * @description 职责边界、与相邻文件关系、关键约束或坑（非显然时写；中文，数行内）
 */
```

- 简单文件（barrel re-export、纯 config）可只留 `@file` 一行。
- 测试文件：`@file` / `@description` 写清测的是哪个单元、覆盖哪些场景。

### 1.2 导出与内部

**导出函数**必须有 JSDoc，至少一句话说明承诺；类型签名看不出的契约必须写明（副作用、调用顺序 / 前置条件、错误语义、业务含义或单位）。

```typescript
/** 按 offset 计算目标周的日期范围；offset: 0=下周, -1=本周剩余。 */
export function computeDateRange(offset: number, now?: Date): { start: string; end: string }
```

`@param` / `@returns` 仅在类型无法表达语义时补充，禁止复述类型。

**导出类型 / 常量**：语义非显然时补一句；常量提取时的 JSDoc 见 §2.1。

**内部函数**不强制每函一注。仅在有副作用、隐式契约（顺序、外部状态、特定错误）、或非平凡边界时写。

### 1.3 多步流程骨架

一个函数或顶层脚本出现 **3 个及以上顺序阶段**时，检查是否需要流程骨架，但不机械添加注释。流程较长、阶段边界无法从命名与函数调用直接看出，或阶段之间存在顺序依赖、副作用、失败语义时：

1. 开头一句话概述流程（如 `解析参数 → 选候选 → 剔除已有 → 写盘`）
2. 每个阶段前一行分段注释标出边界
3. 顺序不显然（后步依赖前步副作用、换序会错）时，补一句为什么

短小、线性且命名已表达步骤的流程无需分段注释。无函数边界的平铺脚本更应检查是否需要注释骨架。

### 1.4 禁止复述

```typescript
// ✗  // 收集 body 引用
// ✓  // Gmail 大正文以 attachmentId 给出、body.data 为空，需二次拉取
```

### 1.5 契约变更则同步改注释

行为或对外契约变了，同步更新描述该契约的注释；过期注释比没有更糟。

## 2. 命名

### 2.1 业务魔法值必须命名

有业务含义的数字与字符串字面量提取为命名常量。

- **跨文件共享** → 放进所属领域模块或其公共入口，并附简短 JSDoc（含义 / 单位 / 取值来源）
- **模块内多处使用，或不宜重复计算** → 放在模块级（import 之后、逻辑之前）
- **仅服务于一个局部逻辑** → 放在该逻辑附近的最窄合理作用域

**例外**（含义自明、不必提取）：`0` / `1` / `-1` 作循环增减或基本索引；`10` 作 `parseInt` 基数；仅在紧邻局部使用、且上下文已完整表达含义的字面量。

**判断标准**：常量名比字面量本身更能表达业务含义，或该值需要跨处保持一致时提取（如 `ORDER_STATUS_PAID` vs `1`、`RETRY_MAX_ATTEMPTS` vs `3`）；常量名不能提供额外语义时不必提取。

### 2.2 跨边界符号带业务域前缀

跨模块、跨 package、或进入公共 barrel 的**常量 / 错误码 / 类型**命名，须从更大作用域保证唯一：前缀挂在**符号名**上，避免全局裸 `STATUS` / `NOT_FOUND` 等。

业务词全拼；仅使用行业公认缩写（HTTP / URL / ID / API / UUID / DB 等），禁止自造缩写（如 `USR_STS`、`AuthMgr`）。

```typescript
// ✗ 太泛，未来同名概念会撞车
STATUS_CODES.ACTIVE
ERROR_CODES.NOT_FOUND

// ✓ 前缀在对象名或成员名上，二选一或组合，保证更大作用域唯一
USER_STATUS_CODES.ACTIVE
ERROR_CODES.USER_NOT_FOUND
```

类型同步前缀化：`UserStatusCode` 而非 `StatusCode`。

**豁免**：

- 模块 / 包内私有（未跨边界导出）——无撞车风险
- package 名本身已是 namespace（如 `@app/inference` 内的 `InferenceClient`、`PROVIDER_NAMES`）——不必再叠包名前缀，除非实际 import 冲突

## 3. 类型按数据语义选型

按**数据在业务里的含义**选类型工具，不为「看起来灵活」而堆联合或泛型。

- **未提供** → 可选字段 `?:`；**明确可空** → `T | null`。避免无语义差别的 `T | null | undefined`；若边界输入已是三态，读入后尽快收窄。
- **有限合法值** → 字符串字面量联合（如 `status: 'pending' | 'paid'`），避免宽 `string` 承载枚举语义。
- **变体形态 / 字段集合不同** → 判别式联合；不要用「一个类型 + 大量 optional」假装多种形态。
- **容器 / 工具随元素类型变化** → 泛型。**业务多形态** → 联合或判别式联合，勿用 `Foo<'a'> | Foo<'b'>` 硬套业务建模。
- **不可信边界**（外部输入、反序列化结果、第三方 payload）先视为 `unknown`，经 schema、type guard 或显式检查后收窄到业务类型。仅当无法控制的第三方接口确实以 `any` 暴露时，才在适配边界短暂接收 `any`；不得向业务代码传播。

## 4. 函数参数：调用处意图自明

### 4.1 避免不透明的布尔位置参数

`fn(data, true)` 在调用处无法表达意图。遇到这类布尔 flag，按优先级替代：

1. 拆成语义明确的函数（`queryByRange` / `queryAll`）
2. 字符串字面量联合（`mode: 'strict' | 'loose'`）
3. options 对象字段

参数本身表达固有二态属性（如 `setEnabled(enabled)`）、调用处已有具名字段，或由框架签名规定时，可以使用 boolean。

### 4.2 防止参数爆炸

按**设计意图**判断，不机械数参数个数。

**可直传位置参数**：1–2 个语义清晰的必选；或业务字段与上下文分离的 `fn(args, ctx)`（`args` 为业务字段包，`ctx` 为请求/运行上下文，优于把 ctx 塞进 args）。

**应打包为对象并解构**：参数较多或可选较多；多个同类型易传错序；参数语义在调用处不直观；options / builder 场景。

```typescript
// ✗  createEntry(title, start, end, date?, location?)
// ✓  createEntry({ title, start, end, date, location })
// ✓  createEntry({ title, start, end }, ctx)
```

框架 / 中间件规定的 handler 签名豁免，不改造成对象参数。

## 5. 结构决策

### 5.1 复用看语义，不看代码相似度

语义完全相同必须复用；代码相似但语义不同可以不复用。提取前先确认「这几处是同一个**概念**」，而不是「这几处代码长得像」。

启发（非硬门槛）：同一概念出现约 3 次再提取；仅 2 处且趋势不明可暂时保留重复——避免为复用而复用。

### 5.2 switch：异构保留，同构纯数据才查表

分支**异构**（各 case 控制流或数据构造方式不同）时，switch 是合适形式——**不要为形式统一而改写成查找表**。

**同构**分支同时大致满足以下条件，才值得改为查找表：

1. case 数量较多或预期持续增长
2. 映射关系为纯数据，可用 `Record` / `Map` 表达

少量同构 case，或每分支含函数调用 / 副作用的，switch 已足够清晰。

### 5.3 已有 barrel 则走 barrel

子目录（或 package 的 public 入口）**已存在** barrel（如 `index.ts`）时，跨目录引用必须经由 barrel，禁止深路径 import。同目录内相对导入不受此约束。

```typescript
// ✗  import { ERROR_CODES } from '../constants/error-codes'
// ✓  import { ERROR_CODES } from '../constants'
```

**不**要求每个目录都建 barrel。新建 barrel 仅当该目录已有稳定对外 API、且至少两处跨目录消费时再建；注意避免 barrel 造成循环依赖。

## 6. 契约变更：默认一次切齐

**默认**：本变更能覆盖的调用方、本仓符号、本仓存储/配置形状，直接切到新契约——删旧名、旧字段、旧分支，不留并行路径。

**兼容、双读/双写、静默 fallback 不是默认**。仅当仍存在真实约束时才允许，且须在代码旁注或 PR 中写明：

1. **兼容对象**（外部调用方 / 未迁移的持久化行 / 不可控的第三方 payload 等）
2. **为何本迭代不能一次切开**
3. **退出条件**（迁完删双读、版本/日期、flag 下线等）

没有退出条件的「暂时兼容」视为不允许。

```typescript
// ✗ 本仓一次 PR 能改完，仍双读「以防万一」
const title = row.title ?? row.name

// ✓ 已确认库内仍有旧行，且本迭代不迁数据——写明对象与退出条件
// 兼容：历史 row.name；迁完 scripts/migrate-title 后删本分支
const title = row.title ?? row.name
```

**区分**：

- **协议/字段兼容**（新旧契约并行）→ 上列例外 + 退出条件
- **运行时失败降级**（依赖故障时的产品行为）→ 写在 PRD/模块策略，**不是**用兼容层代替修编程错误

点名坏味道：未核实旧数据是否仍存在就加 `??` / 旧键；内部重命名后仍导出旧名「以防万一」；`catch` 后 fallback 默认值继续跑、掩盖本应失败的不变量。
