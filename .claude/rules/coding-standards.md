# 代码规范

命名与类型表达「是什么」；注释表达「为什么 / 约束」；结构选择跟语义走；契约变更默认一次切齐。注释默认中文。可 lint 化的约定优先做成 lint。

## 1. 注释：补命名与类型给不了的信息

注释只写意图、分步、顺序约束、副作用、跨行不变量、与邻模块边界。命名 / 类型已表达的不写；有上述信息时必须写，不得以「名称自解释」省略。契约变了同步改注释；过期注释比没有更糟。

自检：遮住代码只读注释，能否得到代码给不了的信息？不能 → 删；该有却没有 → 补。

```typescript
// ✗  // 收集 body 引用
// ✓  // Gmail 大正文以 attachmentId 给出、body.data 为空，需二次拉取
```

### 1.1 文件头

`src/**` 与测试文件均须以 JSDoc 文件头开头（置于 import 之前）：

```typescript
/**
 * @file 一句话：这个文件是什么 / 管什么
 * @description 职责边界、与相邻文件关系、关键约束或坑（非显然时写；中文，数行内）
 */
```

简单文件（barrel、纯 config）可只留 `@file`。测试文件写清测哪个单元、覆盖哪些场景。

### 1.2 导出与内部

**导出函数**必须有 JSDoc，至少一句话说明承诺；类型看不出的契约写明（副作用、调用顺序 / 前置条件、错误语义、业务含义或单位）。`@param` / `@returns` 仅在类型无法表达语义时补充，禁止复述类型。

**导出类型 / 常量**：语义非显然时补一句；常量 JSDoc 见 §2.1。

**内部函数**不强制每函一注；有副作用、隐式契约或非平凡边界时写。

### 1.3 多步流程骨架

函数或顶层脚本出现 **≥ 3 个顺序阶段**，且阶段边界或顺序依赖无法从命名直接看出时，写流程骨架：开头一句话概述（如 `解析 → 筛选 → 写盘`）；每阶段前一行分段注释；顺序不显然时补为什么。短小线性、命名已表达步骤的无需分段。平铺脚本无函数边界，更应检查是否需要骨架。

## 2. 命名

### 2.1 业务魔法值必须命名

有业务含义的数字与字符串字面量提取为命名常量——常量名比字面量更能表达业务含义，或该值需跨处一致时提取。

- **跨文件共享** → 所属领域模块或其公共入口，附简短 JSDoc（含义 / 单位 / 取值来源）
- **模块内多处使用，或不宜重复计算** → 模块级（import 之后、逻辑之前）
- **仅服务一个局部逻辑** → 该逻辑附近最窄合理作用域

**例外**：`0` / `1` / `-1` 作循环增减或基本索引；`10` 作 `parseInt` 基数；紧邻局部且上下文已完整表达含义的字面量。

### 2.2 跨边界符号带业务域前缀

跨模块、跨 package、或进入公共 barrel 的**常量 / 错误码 / 类型**，前缀挂在符号名上，保证更大作用域唯一。业务词全拼；仅用行业公认缩写（HTTP / URL / ID / API / UUID / DB 等），禁止自造缩写。

```typescript
// ✗  STATUS_CODES.ACTIVE  /  ERROR_CODES.NOT_FOUND
// ✓  USER_STATUS_CODES.ACTIVE  /  ERROR_CODES.USER_NOT_FOUND
```

类型同步前缀化：`UserStatusCode` 而非 `StatusCode`。

**豁免**：未跨边界导出的私有符号；package 名已是 namespace（如 `@app/inference` 内的 `InferenceClient`）——不必再叠包名前缀，除非实际 import 冲突。

## 3. 类型按数据语义选型

按数据在业务里的含义选类型，不堆「看起来灵活」的联合或泛型。

- **未提供** → `?:`；**明确可空** → `T | null`。避免无语义差别的 `T | null | undefined`；边界已是三态则读入后尽快收窄。
- **有限合法值** → 字符串字面量联合（如 `status: 'pending' | 'paid'`），避免宽 `string` 承载枚举语义。
- **变体形态 / 字段集合不同** → 判别式联合；不用「一个类型 + 大量 optional」假装多形态。
- **容器 / 工具随元素类型变化** → 泛型。**业务多形态** → 联合或判别式联合，勿用 `Foo<'a'> | Foo<'b'>` 硬套。
- **不可信边界**（外部输入、反序列化、第三方 payload）先 `unknown`，经 schema / type guard / 检查后收窄。仅第三方确实以 `any` 暴露时在适配边界短暂接收；不得向业务代码传播。

## 4. 函数参数：调用处意图自明

### 4.1 避免不透明的布尔位置参数

`fn(data, true)` 无法表达意图。按优先级：拆成语义明确的函数 → 字符串字面量联合 → options 字段。固有二态（如 `setEnabled(enabled)`）、调用处已有具名字段、或框架签名规定时，可用 boolean。

### 4.2 防止参数爆炸

按设计意图判断，不机械数参数个数。

**可直传**：1–2 个语义清晰的必选；或业务与上下文分离的 `fn(args, ctx)`（`args` 业务字段包，`ctx` 请求/运行上下文）。

**应打包为对象并解构**：参数或可选较多；同类型易传错序；调用处语义不直观；options / builder。

```typescript
// ✗  createEntry(title, start, end, date?, location?)
// ✓  createEntry({ title, start, end, date, location })
// ✓  createEntry({ title, start, end }, ctx)
```

框架 / 中间件规定的 handler 签名豁免。

## 5. 结构决策

### 5.1 复用看语义，不看代码相似度

语义完全相同必须复用；代码相似但语义不同可以不复用。提取前确认是同一**概念**。启发：约出现 3 次再提取；仅 2 处且趋势不明可暂留重复。

### 5.2 switch：异构保留，同构纯数据才查表

分支**异构**（控制流或数据构造方式不同）时用 switch。**同构**且 case 较多或持续增长、映射为纯数据时，可改为 `Record` / `Map`。少量同构 case，或分支含调用 / 副作用的，switch 即可。

### 5.3 已有 barrel 则走 barrel

子目录或 package public 入口**已存在** barrel 时，跨目录引用必须经由 barrel，禁止深路径 import。同目录相对导入不限。

不要求每个目录都建 barrel；仅当已有稳定对外 API、且至少两处跨目录消费时再建。注意避免循环依赖。

## 6. 契约变更：默认一次切齐

**默认**：本变更能覆盖的调用方、本仓符号、本仓存储/配置形状，直接切到新契约——删旧名、旧字段、旧分支，不留并行路径。

**兼容、双读/双写、静默 fallback 不是默认。** 仅当同时满足才允许：

1. **仍有无法同步改掉的在用方**（外部客户端、已发布 API/URL、无法批量迁移的存量数据等）
2. **不做会实质受损**（失败、错误数据、权限/安全），而非「旧写法略不方便」
3. **有可验证的退出条件**（迁完即删、版本门槛、截止日期）

允许时须在代码旁注或 PR 写明：兼容对象、为何本迭代不能一次切开、退出条件。没有退出条件的「暂时兼容」视为不允许。

实现上：现行路径是主路径；兼容层只桥接、集中一处，禁止散落 `|| oldPath` / `if (legacy)`；文档与模版只写现行。

```typescript
// ✗ 本仓一次 PR 能改完，仍双读「以防万一」
const title = row.title ?? row.name

// ✓ 已确认库内仍有旧行，且本迭代不迁数据——写明对象与退出条件
// 兼容：历史 row.name；迁完 scripts/migrate-title 后删本分支
const title = row.title ?? row.name
```

**区分**：协议/字段兼容（新旧契约并行）→ 上列例外 + 退出条件。运行时失败降级（依赖故障时的产品行为）→ 写在 PRD/模块策略，不用兼容层代替修编程错误。
