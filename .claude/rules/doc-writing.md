# 文档写作规范

目标：**只写现行、有用、本篇该管、可照着做的内容。**

---

## 写什么

| 写 | 要求 |
| --- | --- |
| **现行做法** | 现在怎么配置、调用、填字段、跑命令 |
| **可执行事实** | 配置值 / 路径 / 命令、操作步骤、验证方法 |
| **边界** | 适用范围写清即可，到此为止 |
| **必要的反向提示** | 仅当易踩或后果重、且正向说不清时，**一条**最短「勿…」 |

每段应至少提供以上信息之一。删掉后不影响照着操作或排查的句子，删掉。配置块前后不要再用长句重复解释配置本身。

---

## 不写什么

| 不写 | 原因 |
| --- | --- |
| 一串「不要做 X」 | 反例无限，冲淡重点；正向与边界已能推出的不必再列 |
| 改动过程叙述 | 「删了什么 / 挪了什么 / 从 A 改成 B」是 commit message 的活；文档只写**改后现状** |
| 「无 X」类空否定 | 某项不存在时直接不提，勿写「无 secret」「没有 `.env`」 |
| 已删除概念的墓碑 | 「已废弃可删」「以前叫 X」仍占认知，还像有效 |
| 工程记忆里已有的约定 | Agent 会加载 `CLAUDE.md` / `AGENTS.md`；勿抄、勿「详见某某节」 |
| 工具链 / 语言 / 平台常识 | 读者已知 |
| 与本仓无关的邻仓、外部流程、边界外故事 | 除非缺了就无法在本仓完成操作 |
| 本篇职责外的内容 | 格式页只写格式；清单页只收条目 |

历史与沿革 → git / 变更记录，不进日常用法与格式说明。

---

## 正向描述优先，不穷举反向约束

把一件事正向描述清楚、并界定好边界，就到此为止。不要再追加一串反向的「不要做 X」。

反向情况可以无限列举；只有当某个反例**确有必要**时才写，即满足以下之一：

- 容易踩（违反直觉、是常见错误）
- 后果重（踩了代价大、难恢复）
- 正向描述无法自然涵盖它

例：写清楚「deploy-verify 只跑只读探测、可反复跑」并给出允许的命令清单后，就不必再列「不要 POST、不要点删除按钮、不要写 DB……」——这些都由「只读」自然推出。但「不要直接打新 tag 兜底」值得单独写，因为它违反直觉、且代价是污染历史。

---

## 只写结果状态，不写改动过程

改完文档只描述**改动后的现状**，不描述改了什么、删了什么、挪了什么。

| | 写法 |
| --- | --- |
| 反例 | 「旧版接口已从路由表删除，对应的处理函数也已移除，现只保留新版接口。」 |
| 正例 | 「只保留新版接口。」 |

例外：某步骤还需单独验证（如「映射还没删，需去控制台确认」），或有独立于本次改动、值得留痕的决策理由。

---

## 已删除内容

**默认：整名省略**（字段 / 入口 / 路径 / 命令均不出现）。

同时满足则省略：

1. 实现与契约已不认  
2. 按文档新建 / 接入时碰不到  
3. 无仍在进行的迁移窗口（或迁移已单独成篇）

**例外**——读者仍可能撞上时，一句指向现行，**不展开旧语义**：

| 情况 | 写法 |
| --- | --- |
| 本地/上游可能残留旧名且会误导 | 「请用 B，勿用已移除的 A。」 |
| 对外 API / 链接曾广泛传播 | 变更说明或兼容层；主路径文档只写现行接口 |
| 迁移仍常见 | 单独「迁移」小节；主表不挂废弃列 |

删功能后：实现不认 + 新人碰不到 → **抹掉该名**，不要改成 deprecated。

---

## 自检

写完或改完问四句：

1. 写的是**现在**怎么做，还是历史 / 废名 / 邻仓故事 / 改动过程？  
2. 这句是否已在工程记忆或常识里？（有则删）  
3. 是否属于**本篇**职责？（否→挪走或删）  
4. 删掉后是否仍不影响照着操作或排查？（不影响→删）
